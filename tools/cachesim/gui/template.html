What the model does

  • Trace-driven and functional. A stream of memory accesses is replayed through the caches. Each access is a hit or a miss at each level, and is charged the latency of the level that served it. There is no pipeline, no prefetcher and no queueing.
  • Hierarchy. Each core has a private L1D and a private L2 that contains everything in its L1. Cores are split evenly into L3 groups (a CCX or a CCD). Each group shares one L3, which is filled on every miss. An optional L4 is shared by all groups and behaves like a separate cache die beside the processor.
  • Coherence. A directory records which cores hold each line. A write invalidates every other copy. A read of a line another core has modified is served core to core. Inside a group this costs one L3 latency; across groups it costs two L3 latencies plus the hop.
  • Latencies. Memory costs the L3 latency plus a fixed time in nanoseconds, so it costs more cycles at a higher clock. A remote L3 or another group costs 2 × L3 + hop. An L4 hit costs L3 + L4.
  • Overlap. Real cores overlap some misses. The overlap setting scales the part of each latency beyond an L2 hit. 1 means no overlap. About 0.36 matches the stall per removed miss inferred from Lam's libx264 measurement (130 cycles against about 358 at 4.2 GHz), as discussed in Part IV of the paper.
  • Time. The estimate is the largest of four limits: the slowest core's latency-bound time, L3 bytes divided by L3 bandwidth (bytes per cycle per active core), DRAM bytes divided by DRAM bandwidth, and link bytes divided by link bandwidth.
  • Energy. A dynamic estimate from per-event energies. The default event energies are illustrative placeholders, not measurements: L1 5, L2 20, L3 100, L4 300 and DRAM 2000 pJ per access. The link default of 2 pJ/bit is AMD's figure for the Zen 1 die-to-die link (Naffziger et al., ISSCC 2020). Set your own values before you quote energy.
  • Warm-up. Random, sequential, stride and hot/cold workloads first fill the caches with a separate stream, then measure. Matrix multiply, graph traversal, ping-pong and traces are measured from a cold start.

Where the default values come from

  • L1 4 cycles, L2 12, L3 47; memory 47 cycles + 74 ns. 7-cpu.com measurements of a Zen 3 Ryzen 5 5600G. The cache sizes and ways are the same source's: 32 KB 8-way L1D, 512 KB 8-way L2, 16-way L3.
  • Zen 2 style L3 at 39 cycles. 47 cycles minus the 7–8 cycles that Chips and Cheese found unifying the L3 added from Zen 2 to Zen 3. It is a derived value, not a measurement.
  • Stacked 96 MB L3 at 51 cycles. 47 + 4. AMD's ISSCC 2022 figure, confirmed independently on three generations.
  • Planar 96 MB at 59 cycles. An assumption. No source measures a 96 MB planar L3; sweep the L3 latency to test it.
  • L4 at 22 ns. Chosen so that a hit in the L4 totals about 34 ns, Lam's measurement of Intel Broadwell's side-by-side eDRAM cache.
  • Hop 9 ns. AMD gives under 9 ns for the round trip between a Rome compute die and the I/O die (Naffziger et al.). Zen 2 CCX-to-CCX transfers are modelled with the same hop, which is an assumption.
  • 32 B per cycle per core of L3 bandwidth. AMD ISSCC 2022, slide 20. 51.2 GB/s DRAM is two DDR4-3200 channels. 55 GB/s link is Naffziger et al.'s effective figure per Rome compute-die link.
  • 4 GHz, 8 cores, 32 MB L3 as two 16 MB halves or one unified cache. The group's experiment plan for Zen 2 and Zen 3 style configurations.

What the model cannot tell you

  • It does not reproduce AMD's real replacement policy, prefetchers, victim-cache behaviour or physical address mapping. Absolute hit rates will differ from hardware; differences between configurations are the useful output.
  • There is no instruction timing, so it gives no IPC. Real programs replayed from a Valgrind Lackey trace report misses per thousand instructions instead.
  • It models 3D stacking only through its capacity and latency. It does not model heat, voltage or clock limits; set the clock by hand to test them.
  • The same simulator runs at full speed as a command-line C++ program (tools/cachesim). Both versions give identical counts for the same settings.
